The Manus
Website Manual

A no-coder's guide to building, launching and managing client websites.

Version 1.0 — August 2026

What this manual is for

This is the standard process for building websites for clients using Manus. You do not need to be a web developer.

You do need to know: what you are building, what Manus should handle, what another system should handle, who owns everything, how the client will update things later, and how you get out if something goes wrong.

The objective is not to build the world's cleverest website. The objective is to build a good website, get it live, make sure it works, and avoid creating a bloody nightmare six months later.

Phase One

Foundations

What you are building, what to collect, and who owns what. Get this wrong and everything after it is built on sand.

01

Part 1

The Golden Rule

Manus builds the website. It does not have to run the client's entire business.

This one rule prevents most problems.

Construction company website?Build it in Manus.
Pub with weekly events?Build it in Manus and make Events editable.
Bike-tour company with a booking system?Build the website in Manus and connect the booking system.
Online shop, hundreds of products?Build the storefront in Manus. Use Shopify to manage the actual commerce.
One-off payment or simple subscription?Manus + Stripe may be enough.
Complex custom software, thousands of users?Stop. This is no longer a normal website job.

Manus currently supports managed hosting, databases, file storage, authentication, custom domains, analytics, Stripe, Shopify, REST APIs and other full-stack functionality. That does not mean we should use all of it on every website. Simple wins.

02

Part 2

First Decision: What Are We Actually Building?

Before touching Manus, put the website into one of these buckets.

Type A — The Simple Business Website

Builder, electrician, consultant, recruiter, accountant, commercial furniture business, local service company. Typical pages: Home, About, Services, Projects, Testimonials, Contact.

Verdict: Manus. Keep it simple. No database unless there is a reason for one.

Type B — The Frequently Updated Website

Pub, restaurant, club, venue, recruitment company, accommodation business, events business. Things that change: events, menus, jobs, specials, projects, team members, news.

Verdict: Manus + structured database. Do not bury information that changes every week inside the page design.

Manus projects can use a managed MySQL database, and records can be viewed, added, edited and deleted through its data interface. Better still, if the client needs to update the content themselves, build them a deliberately simple admin page. Example: clientwebsite.com.au/admin. They log in and see Events, Add Event, a handful of fields, Save. That's it.

Do not give Dave from the pub the keys to the entire website because he wants to change Saturday night's band.

Type C — The Booking Website

Mountain biking, tours, appointments, accommodation, classes, experiences. First question: does the client already use booking software?

If yes: do not rebuild it. Connect or embed the existing booking platform. Manus can communicate with third-party systems through REST APIs where required.

Your job is: website → beautiful information → obvious BOOK NOW button → existing booking system. Do not accidentally build Expedia.

If they don't have booking software, assess that separately before promising anything.

Type D — E-Commerce

100 products, stock levels, sizes, colours, discount codes, shipping, refunds, collections.

Recommended setup: Manus = website/storefront. Shopify = commerce engine.

Manus officially supports connecting a Shopify commerce backend, including products, collections, inventory and checkout. The client changes products in Shopify. Manus displays the shop. Shopify handles the serious commerce machinery.

Do not make someone's stock control system dependent on asking an AI agent to change a webpage.

Type E — Simple Payments

A $100 booking deposit, paid consultation, membership, fixed-price service, simple subscription. Consider Manus + Stripe. Manus can create and test Stripe payments in a sandbox before connecting the real Stripe account.

Type F — "This Is Starting to Sound Like Software"

Warning signs: users need individual dashboards, different permission levels, live availability, synchronising with three systems, customers creating accounts and managing orders, thousands of database records, complex calculations.

Manus can technically build sophisticated web applications. But commercially, stop calling this a website. Scope it separately.

04

Part 4

Ownership: Do This Properly

This is boring. It is also where future disasters come from.

The client should own

  • Domain name
  • Shopify account
  • Stripe account
  • Booking platform
  • Google Business Profile
  • Important third-party business accounts

You can have access. They should own them. Why? If the relationship ends, their business shouldn't collapse.

Domain Rule

For client work, the recommended default is: keep the domain with an independent domain registrar.

Manus allows an existing domain or subdomain to be connected using DNS records, normally an A record and/or CNAME, and automatically provisions SSL/HTTPS once connected. Manus also allows domains to be purchased directly through Manus. I would normally not do that for client domains. Keeping the domain independent makes ownership clearer and makes moving the website later easier.

Important: Don't Murder Their Email

When connecting a domain, change only the DNS records required for the website. Do not randomly delete MX records, SPF records, DKIM records, TXT records, Microsoft 365 records or Google Workspace records.

If you don't know what a DNS record does: leave it alone. Take screenshots of the existing DNS setup before changing anything.

The Build

Brief it properly, review it before the client sees it, and put anything that changes weekly into a database, not a page.

05

Part 5

Building the First Version

Don't start with "Build me a website for ABC Construction." It may work, but you're making Manus guess half the job. Give it a proper brief instead.

Master Build Prompt
Build a complete professional website for [BUSINESS].

The business is [DESCRIPTION].

Primary audience: [AUDIENCE].

The primary goal of the website is to get visitors to [ACTION].

Required pages:
[PAGES]

Brand direction:
[STYLE]

Use the supplied logo, photographs, brand assets and business information exactly where appropriate.

The site must feel modern, credible and human. Avoid generic AI website styling, excessive gradients, unnecessary animations, huge amounts of empty space and generic corporate language.

Prioritise:

- strong mobile experience;
- simple navigation;
- clear calls to action;
- readability;
- trust;
- fast page loading;
- SEO-friendly page structure;
- accessibility;
- obvious contact information.

Do not invent testimonials, awards, accreditations, projects, statistics, employees, locations or claims.

If information has not been supplied, use clearly marked placeholders rather than making factual claims.

Build the complete first version and then give me a list of anything still required from the client.

Manus supports conversational editing and direct visual controls for styling, typography, spacing, borders and similar changes.

07

Part 7

Mobile

Do not consider mobile an optional final check. For many small businesses, mobile is the website. Manus provides desktop and mobile preview modes. Check every important page on mobile.

Look for: giant headings, buttons falling off screens, unreadable menus, stretched images, strange gaps, forms that are horrible to complete, phone numbers that can't be tapped, pop-ups covering the screen.

Then test the actual published site on your own phone.

08

Part 8

Forms

Typical form: Name, Email, Phone, Message. For some businesses: Service required, Preferred date, Location, Budget, Upload file.

Manus supports backend processing and database storage for form submissions. It also supports event-driven notifications when website data changes.

Recommended Form Instruction
When someone submits this form:

1. validate the required fields;
2. save the submission;
3. send a notification to [EMAIL];
4. show the visitor a clear confirmation message;
5. prevent accidental duplicate submissions;
6. make the form work properly on mobile.

Then TEST IT. Use your own details. Confirm: submission succeeds, email arrives, database record exists if required, confirmation appears, reply/contact details are usable.

Never assume a form works because it looks like a form.

09

Part 9

Frequently Changing Content

This is where we stop editing pages manually. Imagine a pub. The homepage shows THIS WEEK: Friday, Karaoke. Saturday, The Bogans. Sunday, Roast & Live Music. If these are hard-coded into the homepage, someone has to redesign the page every week. Bad system.

Instead, create an Events database

Fields: Event Name, Date, Start Time, Description, Image, Booking URL, Category, Published, Featured.

Events Instruction
The events section must automatically display future events from the Events database ordered by date. Do not display expired events unless they are specifically marked to remain visible.

Manus's persistent database is designed for structured information such as products, posts, profiles and similar records.

10

Part 10

Client Self-Editing

There are three models.

Model 1 — You update everything

Best for tiny businesses, infrequent changes, clients who don't want another login, maintenance retainers. Client emails "Change Friday's band to The Pork Chops." You update it. Done. This is the easiest model.

Model 2 — Client edits structured content

Best for pubs, events, vacancies, menus, projects, accommodation, regular news. Build a simple password-protected admin area. Manus supports login systems and role-based restrictions for specific pages such as /admin.

Example admin: Website Manager. EVENTS. MENU. SPECIALS. Nothing else.

Do not build WordPress inside Manus. Give them only what they genuinely need.

Model 3 — Client works inside Manus

Manus has collaborative tasks where invited collaborators can see the work and prompt Manus themselves. I would not use this as the normal client handover model. Because the client who only wanted to change a photo can now tell Manus: "Make the entire website red and add a spinning kangaroo."

Use collaboration when genuinely useful. Use an admin panel for routine content.

Part 12

E-Commerce

When to use Shopify

Use Shopify when products involve inventory, lots of products, variants, shipping, fulfilment, discount codes, collections, or ongoing catalogue management. Manus officially supports Shopify as a commerce backend and can connect products, collections, inventory and checkout.

Recommended architecture: Customer → Manus website → Shopify checkout/commerce.

Client product management: Shopify admin. Website design: Manus. Nice separation.

Part 14

Connecting the Domain

Once the site is approved, go to publishing/custom domain and tell Manus the domain. Example: "Connect this website to www.clientdomain.com.au." Manus provides the DNS records required, normally A and/or CNAME records.

At the domain registrar

  1. Screenshot existing DNS.
  2. Add/change only the required records.
  3. Save.
  4. Wait for DNS to propagate.
  5. Confirm both versions work where appropriate: clientdomain.com.au and www.clientdomain.com.au.
  6. Confirm HTTPS works.

Manus automatically provisions an SSL/TLS certificate after the domain is connected.

15

Part 15

Where Is the Website Actually Hosted?

If you publish normally through Manus, Manus manages the hosting infrastructure. You do not need a separate Netlify, Vercel or AWS account for the standard setup.

The default Autoscale hosting currently uses Google Cloud Run and scales according to demand. Manus also offers Reserved hosting for applications requiring persistent processes.

For ordinary business websites: leave it on Autoscale. Don't touch clever hosting settings because they sound impressive.

Part 16

The Billing Trap

Pay attention to this. Manus currently has two different website cost systems:

Building / Editing

Manus credits

Live Website Usage

Usage-based hosting/cloud/AI/API billing

Each account currently includes monthly allowances, including a cloud allowance. Larger usage can create additional charges. Most importantly:

If there aren't sufficient funds and auto top-up isn't enabled, the website may become temporarily unavailable.

Therefore every live-client checklist includes:

  • Website billing reviewed
  • Payment card valid
  • Auto top-up considered/enabled
  • Usage monitored
  • Client understands ongoing cost arrangement

Do not host 20 client websites under one account and then ignore the billing dashboard for twelve months.

17

Part 17

Who Pays for Hosting?

Pick one model and be clear.

Option A — Included in your maintenance service

You manage Manus hosting, updates, backups, monitoring. Client pays one monthly fee. Simplest client experience.

Option B — Client owns/pays everything

More admin. Cleaner separation.

Option C — Hybrid

Client owns important external accounts. You manage Manus and include normal hosting within a maintenance fee, subject to reasonable usage.

Recommended model for smaller managed clients: Hybrid. Client owns their domain and important business systems. You manage the Manus website.

Analytics

Manus automatically provides built-in website analytics including visitors, page views and traffic sources on published apps.

At minimum, after launch you should be able to answer: Is anyone visiting? Which pages do they visit? Where do visitors come from? Are enquiries coming through?

For clients who rely heavily on marketing, consider their existing Google Analytics or other marketing measurement setup rather than creating competing sources of truth.

20

Part 20

Backups & the Escape Hatch

Never build a business-critical site with no way out. Manus lets you download the entire underlying codebase. It also integrates with GitHub and can create a private repository with two-way synchronisation between Manus and the main branch.

Standard rule: for every serious live client, connect the project to GitHub.

You do not need to become a GitHub developer. Think of it as a spare copy of the website's engine stored somewhere else.

Manus automatically syncs changes made through Manus to the connected repository.

Do not randomly rename or transfer that GitHub repository after connecting it; Manus warns that this breaks its connection.

Part 29

When Not to Use Manus

Think twice if the project requires:

  • Highly specialised enterprise infrastructure
  • Unusual regulatory requirements
  • Mission-critical systems
  • Complex real-time applications
  • Enormous traffic
  • Complicated bespoke commerce
  • Advanced integrations you don't understand
  • Software where failure could seriously harm the client's operation

Manus may still be able to build it. That doesn't automatically mean you should sell it.

Part 30

Troubleshooting

"The domain isn't working."

  1. Correct domain entered?
  2. DNS records match Manus instructions?
  3. Both root and www considered?
  4. DNS propagation complete?
  5. SSL issued?
  6. Existing conflicting records?

Do not start randomly deleting DNS records.

"The client's email stopped working."

Stop. Review any DNS changes. Email normally depends on separate MX/TXT/DKIM/SPF records. Restore anything accidentally removed. If unsure, get technical help.

"The website is down."

  1. Manus service status.
  2. Website usage/billing.
  3. Payment balance.
  4. Domain expiry.
  5. DNS.
  6. Published project.
  7. Recent changes.

Remember: Manus documentation specifically warns that insufficient website funds can make the site temporarily unavailable.

"I changed something and broke the website."

Do not keep prompting wildly. Check GitHub/version history/copy. Work out what changed. Revert or restore known working code/version where possible. Then make the change again properly.

"The client wants something new every day."

Congratulations. You have discovered a maintenance plan. Do not provide unlimited development disguised as "hosting."

Part 31

The FAQ

1. Is Manus actually hosting the website?

Yes, if you publish through Manus. Manus manages the deployment and cloud infrastructure.

2. Do I need another hosting company?

Not for a normally published Manus website.

3. Can I use the client's existing domain?

Yes.

4. Does the domain have to be transferred to Manus?

No. You can keep it with its existing registrar and point the required DNS records to Manus.

5. Can Manus sell me a domain?

Yes. For client work, I generally recommend keeping domain ownership independent.

6. Does Manus provide HTTPS?

Yes. Manus automatically provisions SSL/TLS once the custom domain is connected.

7. How do I change the website after launch?

Open the existing Manus project and describe the change. Manus can edit and redeploy published sites.

8. Does every change require code?

No. Manus is specifically designed around conversational and visual editing.

9. Can my client make changes?

Yes, but decide what type of changes. For regular data such as events, jobs and menu items, use a simple admin interface. For occasional website changes, you can manage them.

10. Can I give clients their own login?

Manus-built apps support registration, login/logout, user management and role-based access to specific sections.

11. Can I create an admin-only page?

Yes. Manus explicitly documents restricting /admin to users with an Admin role.

12. Can Manus store events, products or articles?

Yes. Its database can store structured persistent data.

13. Can the database be edited manually?

Yes. Manus provides a visual data browser where records can be added, edited and deleted.

14. Should a client edit that database directly?

Usually a clean admin interface is better. Less opportunity for carnage.

15. Can Manus handle contact forms?

Yes. Its backend can process forms, store submissions and trigger actions.

16. Can I get notified when someone submits something?

Yes. Manus supports notifications triggered by data changes.

17. Can Manus handle Shopify?

Yes. Shopify is an officially supported integration.

18. Should I build a large online shop purely inside Manus?

I wouldn't. Use Shopify for the commerce engine unless there is a strong reason not to.

19. Can Manus accept payments without Shopify?

Yes. Stripe integration is built in.

20. Can it do subscriptions?

Its Stripe integration supports product and subscription models.

21. Can it connect to booking systems?

If the service exposes an appropriate web/API integration, Manus can connect to REST APIs. A normal booking link or embed may be simpler.

22. Does Manus have analytics?

Yes. Built-in analytics include visitors, page views and traffic sources.

23. Does Manus handle SEO?

It has built-in technical and on-page SEO tooling including prerendering, sitemaps, canonical URLs and SEO analysis.

24. Does that guarantee Google rankings?

No. Absolutely not.

25. Can I export the website?

Yes. Manus says the full codebase can be downloaded.

26. Am I trapped with Manus forever?

The code-export and GitHub options materially reduce platform lock-in. Moving a live application elsewhere may still require technical work.

27. Should every client website have a GitHub backup?

For anything commercially important, yes.

28. Does GitHub mean I need to learn coding?

No. For the basic process, it's primarily the safety copy/version-control layer.

29. Does Manus automatically sync GitHub?

Once connected, Manus documents automatic push/pull synchronisation with the main branch.

30. Can I copy a website before making changes?

Yes. Manus has a Make a Copy feature.

31. What if the client already has WordPress?

Decide whether there is actually a reason to replace it. "AI can rebuild it in five minutes" isn't, by itself, a business case for migration.

32. What happens to old Google rankings when replacing a website?

Preserve important URLs where possible. If URLs change, arrange proper redirects. Do not casually delete pages that already rank.

33. Should I rebuild the website directly on the client's live domain?

No. Build and approve it first. Connect the domain when you are ready to launch.

34. Should I host every client site in my Manus account?

You can, but think commercially. The more client sites sitting under one account, the more responsibility and billing dependency sits with you. Maintain a proper client register.

35. What should be in the client register?

For every site record: Client, Website URL, Manus project, Domain registrar, Domain renewal date, GitHub repository, Booking platform, Shopify, Stripe, Analytics, Client admin users, Maintenance arrangement, Billing arrangement, Launch date.

36. Who owns the website code?

Make this clear contractually. Technical exportability does not replace a clear commercial agreement about ownership.

37. Can Manus hosting cost more as traffic increases?

Yes. Live website hosting uses usage-based billing after included allowances.

38. Can a Manus site go offline because of billing?

Yes. Manus warns that insufficient funds without auto top-up can cause temporary unavailability.

39. Should I enable auto top-up?

For commercially important managed sites, strongly consider it and monitor spend.

40. What happens if Manus disappeared tomorrow?

Your protection is: independently owned domain + GitHub copy + downloadable code + independently owned external systems. That is why we set the architecture up properly from day one.
